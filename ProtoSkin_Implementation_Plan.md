**Primary track:** Generative AI & Creative Tech  
**Secondary fit:** AI-Powered Productivity  
**Team size:** 3  
**Hardware:** HP ZGX Nano (128 GB unified memory)

---

## 1. Project Overview

ProtoSkin is a fully local generative design assistant for rapidly exploring how a product concept could look when manufactured with alternative materials and finishes.

The app takes a 2D wireframe, sketch, CAD-derived render, or depth-style image of a laptop chassis, printer shell, or similar product and produces:

1. A photorealistic material concept image generated with a diffusion model guided by ControlNet.
2. A grounded material screening report based on predefined physical/material properties and deterministic calculations.
3. A short plain-language explanation generated by a local LLM.
4. An optional A/B comparison between the baseline material and a proposed alternative.

Everything runs locally on the HP ZGX Nano. No external AI inference API is required for the demo.

### Important positioning

This is a **rapid concept-visualization and material-screening tool**, not an engineering-grade CAD simulator.

ControlNet is used to strongly preserve the product silhouette, proportions, and major visual structure while changing appearance, texture, finish, and lighting. It does **not** guarantee exact CAD geometry.

The material report is also clearly labeled as a **screening estimate based on stated assumptions**, not a production BOM, FEA result, thermal simulation, or manufacturing quote.

### Core value proposition

Industrial designers often need to explore multiple finish/material concepts before physical prototyping. External rendering services or cloud AI can introduce recurring costs, latency, and IP-governance concerns.

ProtoSkin demonstrates how local AI hardware can support fast visual iteration while keeping pre-release product imagery and design inputs on local infrastructure.

### Success criteria for the demo

- Upload a wireframe/sketch/CAD-derived image.
- Select a baseline material and a candidate material.
- Optionally select finish, texture, and color.
- Click **Generate Concept**.
- Produce a materialized photorealistic concept image whose overall silhouette and major design structure remain recognizable.
- Produce grounded material metrics derived from the shared material data.
- Generate a short LLM explanation using those calculated metrics.
- Display an A/B comparison between the baseline and candidate material.
- Show that inference is running locally on the ZGX Nano with zero cloud AI calls.
- Complete the full flow reliably in a reasonable live-demo time.

## 2. System Architecture

```text
[ Browser / Studio UI ]
          |
          v
[ FastAPI Gateway / Orchestrator ]
      |              |                 |
      |              |                 |
      v              v                 v
[ Visual Engine ] [ Material Engine ] [ Local LLM ]
 Diffusion +       deterministic       explanation
 ControlNet        calculations        only
      |              |                 |
      +--------------+-----------------+
                     |
                     v
       [ Combined Material Concept Result ]
```

### Component roles

- **Visual Engine:** transforms the product appearance while being structurally guided by the input image.
- **Material Engine:** computes grounded screening metrics from known input assumptions and material properties.
- **Local LLM:** explains those metrics in natural language; it does not invent the metrics.
- **Gateway/UI:** coordinates the workflow and presents the result.

### Execution strategy

Build the first stable version **sequentially**:

1. Run material calculations.
2. Generate the concept image.
3. Generate the LLM explanation.
4. Return the combined result.

Only experiment with concurrent model execution if the sequential flow is already stable.

Reliability matters more than demonstrating simultaneous execution.

## 3. Shared Contracts — Lock Before Coding

### 3.1 Shared Material Definitions

Create one shared file, for example:

```text
/shared/materials_config.json
```

Each material contains two groups of data.

### Visual properties

Used by the Visual Engine:

- internal material ID
- display name
- visual description
- default finish
- reflectivity description
- texture description
- preferred prompt fragment
- optional negative-prompt fragment

Example:

```json
{
  "ocean_bound_polymer": {
    "label": "Ocean-Bound Recycled Polymer",
    "visual": {
      "appearance": "fine recycled speckling, dark graphite polymer",
      "finish": "matte",
      "reflectivity": "low",
      "texture": "fine"
    }
  }
}
```

### Analytical properties

Used only by the deterministic Material Engine:

- density or relative density
- estimated raw-material cost per kg, or a relative cost index
- thermal conductivity value or clearly defined tier
- recycled-content percentage if available in the project dataset
- sustainability/manufacturing notes
- source/assumption field

Example:

```json
{
  "density_kg_m3": 1150,
  "raw_material_cost_usd_per_kg": 2.40,
  "thermal_conductivity_w_mk": 0.25,
  "recycled_content_percent": 70,
  "assumption_note": "Hackathon screening dataset; not a supplier quote"
}
```

### Recommended starter materials

Use only 4–5 materials for the demo:

- Recycled Aluminum
- Ocean-Bound Recycled Polymer
- Magnesium Alloy / Recycled Magnesium concept
- Molded Recycled Fiber Composite
- Standard ABS or conventional aluminum as a baseline

Do not add more materials until every existing material works end-to-end.

---

### 3.2 Shared Product Assumptions

To compute meaningful relative metrics, define a simple product-assumption structure.

Example:

```json
{
  "product_type": "13-inch laptop top shell",
  "estimated_shell_volume_cm3": 82,
  "baseline_material": "recycled_aluminum"
}
```

For the hackathon, this can be selected from 2–3 preset product profiles rather than inferred from the image.

Recommended profiles:

- 13-inch laptop shell
- 15-inch laptop shell
- compact printer exterior shell

This makes the calculations deterministic and avoids pretending the model can derive engineering dimensions from a sketch.

### 3.3 Contract A — Visual Generation

**Input: Gateway → Visual Engine**

- base image
- material ID
- finish
- texture option
- optional color
- optional free-text visual prompt
- control mode: `canny` or `depth`

**Output: Visual Engine → Gateway**

- generated image
- generation time
- seed
- control mode
- status
- error message if failed

### Required behavior

The generated image should:

- preserve the recognizable product silhouette
- preserve major proportions and visible structural features
- avoid introducing obvious extra hinges, screens, handles, buttons, or product parts
- mainly change material appearance, texture, finish, lighting, and photographic presentation

The output is a **concept render**, not a geometry-accurate CAD result.

---

### 3.4 Contract B — Material Calculation

**Input: Gateway → Material Engine**

- product profile
- baseline material ID
- candidate material ID

**Output: Material Engine → Gateway**

```json
{
  "baseline_mass_g": 0,
  "candidate_mass_g": 0,
  "mass_delta_percent": 0,
  "baseline_raw_material_cost_usd": 0,
  "candidate_raw_material_cost_usd": 0,
  "raw_material_cost_delta_usd": 0,
  "thermal_comparison": "",
  "recycled_content_percent": 0,
  "assumptions": [],
  "status": "success"
}
```

### Calculation principles

The Material Engine must use deterministic formulas.

Example mass estimate:

```text
mass = material density × assumed shell volume
```

Example raw-material cost estimate:

```text
raw material cost = estimated mass × material cost per mass unit
```

These are **screening calculations only**.

Do not call the result:

- total BOM savings
- manufacturing savings
- production cost
- engineering validation

Use terminology such as:

- estimated mass difference
- estimated raw-material cost difference
- relative thermal characteristic
- recycled-content indicator

---

### 3.5 Contract C — Local LLM Explanation

**Input: Gateway → LLM Engine**

The LLM receives only grounded information:

- product type
- baseline material
- candidate material
- calculated metrics from Contract B
- assumptions
- manufacturing/sustainability notes from the shared config

**Output: LLM Engine → Gateway**

- 2–4 sentence plain-language summary
- key tradeoff bullets
- structured JSON if supported
- status/error

### Non-negotiable behavior

The LLM must **not invent new numerical values**.

If the calculator says:

```text
mass_delta_percent = -11.8
raw_material_cost_delta_usd = -0.74
```

then the explanation can say:

> Under the same shell-volume assumption, this candidate material is estimated to reduce shell mass by 11.8% and raw-material cost by about $0.74 per shell.

It cannot change those numbers or invent unrelated thermal/sustainability claims.

**Hugging Face model:** `diffusers/controlnet-canny-sdxl-1.0`

Purpose:

## 7. Person A — Visual Engine

### Objective

Convert the input product image into a photorealistic material concept while preserving its recognizable visual structure.

### Recommended stack

Primary implementation:

- Hugging Face Diffusers
- `stabilityai/stable-diffusion-xl-base-1.0`
- `diffusers/controlnet-canny-sdxl-1.0`
- OpenCV for Canny preprocessing

Optional after MVP:

- `diffusers/controlnet-depth-sdxl-1.0-small`
- `Intel/dpt-hybrid-midas` if depth must be estimated from a regular image

ComfyUI can still be used for rapid visual experimentation, but the final shared implementation should use one predictable pipeline/API contract.

For hackathon reliability, get the SDXL + Canny ControlNet path stable before experimenting with FLUX or additional model families.

### Primary preprocessing modes

#### Canny

Best first choice for:

- clean line drawings
- wireframe-like sketches
- product-outline images

#### Depth

Useful for:

- CAD-derived shaded renders
- images with clear 3D structure
- existing depth maps

### MVP recommendation

Implement **Canny first**.

Add depth only after Canny works reliably.

### Prompt assembly

Construct prompts from:

1. shared material visual description
2. selected finish
3. selected texture
4. selected color
5. user's optional visual instruction
6. fixed product-photography suffix

Example:

```text
13-inch premium laptop chassis, ocean-bound recycled polymer,
fine graphite speckling, matte low-reflectivity finish,
clean industrial design, photorealistic studio product photography,
soft controlled lighting, neutral background
```

### Negative prompting

Experiment with restrictions against:

- changed geometry
- extra ports
- duplicate hinges
- extra screens
- extra keyboards
- warped chassis
- text/logo artifacts
- additional product objects

### Control strength

This is one of the most important parameters.

Tune it using the same 2–3 reference inputs.

Goal:

> preserve recognizable structure while allowing realistic material transformation.

### Demo determinism

Use a fixed known-good seed for the primary demo material/input pair.

Random generation can remain available outside demo mode.

### Performance

Optimize for dependable live generation:

- reasonable resolution
- reduced inference steps if image quality remains acceptable
- appropriate quantization/offload only if needed
- warm the model before the demo

Measure:

- first-run generation time
- warmed-run generation time
- memory usage

### Standalone checklist

- [ ] Canny preprocessing works on all shared sample inputs.
- [ ] Generated output preserves recognizable silhouette and major structure.
- [ ] Each demo material has at least one verified good output.
- [ ] Fixed-seed demo output is reproducible enough for presentation.
- [ ] Generation time is measured.
- [ ] Model can be loaded and run entirely locally.
- [ ] Fallback examples are saved and labeled as previously generated outputs.

## 8. Person B — Material Intelligence Engine

### Objective

Produce a credible material-screening result without allowing the LLM to fabricate engineering values.

Person B owns two subcomponents:

1. deterministic material calculator
2. local LLM explainer

### Part 1 — Deterministic calculator

Read:

- baseline material
- candidate material
- selected product profile

Compute:

- baseline estimated mass
- candidate estimated mass
- mass delta
- baseline estimated raw-material cost
- candidate estimated raw-material cost
- cost delta
- thermal comparison
- recycled-content comparison

### Important assumptions

Always attach assumptions to output.

Example:

```text
Assumptions:
- identical shell volume
- material-only estimate
- excludes tooling, coatings, labor, yield, assembly, logistics, and supplier negotiation
- values are hackathon screening inputs, not HP supplier data
```

### Part 2 — Local LLM explainer

Primary local explanation model:

- `Qwen/Qwen3-8B` downloaded from Hugging Face

Fallback if runtime compatibility becomes an issue:

- `Qwen/Qwen2.5-7B-Instruct`

Do not spend hackathon time benchmarking many LLM families for this component. The LLM is an explanation layer, not the core engineering calculator.

The LLM receives the calculator JSON and converts it into a concise explanation.

Example output:

```text
Under the same shell-volume assumption, the candidate polymer is estimated
to reduce shell mass by 11.8% and raw-material cost by $0.74 per unit.
Its thermal conductivity is substantially lower than the aluminum baseline,
so additional thermal-design consideration may be required.
```

### The LLM must never

- generate its own cost number
- generate its own density
- claim a manufacturing process is validated
- claim the product is production-ready
- claim the result is a total BOM saving

### Failure behavior

If LLM output parsing fails, generate a deterministic templated summary from the calculator JSON.

The application must never crash because the LLM produced malformed text.

### Standalone checklist

- [ ] All material calculations are deterministic.
- [ ] Same inputs always produce identical numerical outputs.
- [ ] Every metric includes units.
- [ ] Assumptions appear in the returned JSON.
- [ ] Local LLM explanation reproduces calculator numbers exactly.
- [ ] LLM never invents unsupported numerical claims in repeated tests.
- [ ] Template fallback works with no LLM.

## 11. Risk Register & Fallbacks

| Risk | Mitigation / Fallback |
|---|---|
| Generated image changes too much of the product structure | Increase ControlNet strength, simplify prompt, use known-good input/seed, reduce creative styling |
| SDXL/ControlNet is too slow | Lower resolution or inference steps; warm model before demo; use stable accelerated configuration |
| Live generation returns a bad image | Show a clearly labeled previously generated local output; never present cached output as a live generation |
| LLM invents numbers | Never give it authority to calculate numbers; numbers come only from deterministic Material Engine |
| LLM returns malformed output | Use template-based explanation directly from calculator JSON |
| Material estimates appear too precise | Display assumptions, use approximate language, and report only screening-level metrics |
| Concurrent models create instability | Run sequentially; concurrency is optional only after full pipeline stability |
| Shared material names drift | Single shared material config is the only source of truth |
| Internet unavailable | All models, configs, sample inputs, and dependencies required for the demo must already be local |
| Judges question CAD accuracy | Explicitly position output as concept visualization, not CAD/engineering validation |
| Judges question HP-specific numbers | State clearly that demo data is public/synthetic/hackathon screening data, not confidential HP supplier data |

## 13. ZGX Nano Technical Story

The pitch should emphasize three defensible advantages.

### 1. Local IP handling

Product sketches, CAD-derived renders, and pre-release industrial-design images can be sensitive intellectual property.

Running the visual pipeline locally can help organizations keep these assets within their own controlled infrastructure rather than sending them to a third-party AI inference API.

### 2. No per-generation AI API charge

Once models are downloaded and running locally, the demo does not incur a cloud AI API fee for every generated concept or LLM explanation.

Do not claim the system is "free".

Local inference still has:

- hardware acquisition cost
- power cost
- maintenance cost
- engineering/operations cost

The credible claim is:

> local inference replaces recurring per-request external AI inference charges with locally managed compute.

### 3. Large local model capacity

The ZGX Nano's 128 GB unified memory enables experimentation with larger local generative and language-model workflows than many conventional developer machines can comfortably host at once.

Do not claim that every 16–24 GB GPU will necessarily OOM.
